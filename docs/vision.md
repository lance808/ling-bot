# 视觉（真实聊天图片识别链路）

> 实现与契约：[vision-contract.md](./vision-contract.md)（接口）、本文（用法与边界）。
> 状态：**已实现并接入聊天回合**（2026-10-23）。

## 1. 它解决什么问题

改造前，QQ 里发一张图，机器人看到的只有一句 `[图片]`：

| 环节 | 改造前 | 改造后 |
| --- | --- | --- |
| 事件文本 | `segmentsToText` 把 image 段渲染成 `[图片]`，`file`/`url`/`mime` 全丢 | 文本仍是 `[图片]`（不变），但媒体元数据另有去路 |
| 会话历史 | `append()` 只存文本与 `replyTo` | 另存六个媒体元数据键（**不含 URL、不含 base64**） |
| 提示组装 | `buildMessages` 只产出字符串 content | 有图时产出 `[text, image_url]` 数组 |
| 模型请求 | 从未包含过图片 | 真实携带 `image_url`（`data:image/...;base64,...`） |
| 能力探测 | 成功只说明"接受图片输入" | 与真实链路分开显示，且**不等于**已读图 |

最后一条是这次刻意区分开的：探测是**一次独立的小请求**，聊天链路走的是
**另一条路**（取图 → 预算 → 组装 → 上游）。两条都通了才算真的能读图，
所以界面上它们是两个独立的块。

## 2. 打开它

界面：**配置 → 视觉**。

```json
{
  "vision": {
    "enabled": false,
    "maxImagesPerTurn": 3,
    "maxHistoryImages": 2,
    "maxBytes": 4194304,
    "maxTotalBytes": 8388608,
    "maxPixels": 36000000,
    "timeoutMs": 8000,
    "historyWindow": 6,
    "includeQuoted": true,
    "cacheTtlMs": 300000
  }
}
```

**默认关闭**。理由有两条，都关于钱：

1. 每张图都按 token 计费。一个活跃群一天几百张图，全提交是笔真金白银；
2. 用户升级后如果忽然开始为图片付费，他会认为这是 bug，而且很难自证。

关掉之后的行为要说清楚（界面也写了）：

- **不取图**：不再调用网关 `get_image`，不再抓任何 URL；
- **不提交**：请求体里没有 `image_url`；
- 消息文本里仍然是 `[图片]` 这个占位，并额外附一句"你看不到图里的内容，
  不要猜"——否则模型要么编造，要么突兀地说"我看不见图片"。

## 3. 图片预算（这是成本控制的主战场）

| 项 | 默认 | 硬上限 | 说明 |
| --- | --- | --- | --- |
| `maxImagesPerTurn` | 3 | 4 | 本轮消息最多几张 |
| `maxHistoryImages` | 2 | 3 | 历史/引用最多几张 |
| `maxBytes` | 4 MB | 4 MB | 单张字节上限 |
| `maxTotalBytes` | 8 MB | 8 MB | 一回合总字节 |
| `maxPixels` | 36,000,000 | 36,000,000 | 单张像素（防图片炸弹） |
| `timeoutMs` | 8 s | 15 s | 单张取图总时限（含 DNS 与每一跳） |
| `historyWindow` | 6 楼 | 8 楼 | 历史回看范围 |
| `cacheTtlMs` | 5 min | 5 min | 内存缓存有效期（不落盘） |

配置允许写到硬上限的 2 倍（"想宽松一点"是合理需求），但运行时一律夹回硬上限；
界面显示的是**夹取后实际生效的值**，并注明"填得更大能保存，但按 X 生效"。

### 一回合最多几张

```
maxImagesPerTurn + maxHistoryImages  =  默认 5 张
单回合图片字节总量                    ≤  8 MB
```

## 4. 挑选顺序与"不重复提交"

优先级就是成本优先级，**不要随手调换**：

1. **本次消息**（用户刚发的，几乎总是最相关）
2. **引用消息**（用户特意引用过来，意图明确）
3. **历史**（只取 `historyWindow` 内、**没提交过**、仍在仓库里的楼层，从新到旧）

第 3 条里的"没提交过"是省钱的关键：提交过的楼层记进
`sessionStore.imagesSeenFloors`（有界 500、随楼层淘汰修剪、**持久化**），
下一回合直接跳过。

没有这一步的话，历史里的图会被**每一回合**重新塞进请求体：
成本按回合线性增长，而模型得到的边际信息几乎为零——它上一回合已经看过那张图了。

## 5. 安全边界

`src/llm/image-fetch.mjs` 是唯一允许"把外部字节拿进来"的地方，四路来源按序尝试：

```
安全的 get_image 缓存名 → inline (base64:// / data:) → 段内 URL → 本地缓存路径
```

每一跳都必须过：

| 边界 | 做法 |
| --- | --- |
| 缓存名形态 | 只接受 `^[\w.+=@-]{1,512}$`，无路径、无盘符、无协议、无 `..` |
| URL 协议 | 仅 http/https，拒绝带凭据的 URL |
| 私网 / 本机 | 字面 IP 与 DNS 解析结果**全部**检查（IPv4/IPv6、IPv4-mapped、NAT64、链路本地）；`.local` / `.localhost` / `.internal` 一律拒 |
| DNS rebinding | 先解析 → 校验全部地址 → **用已校验 IP 直连**（保留 Host 与 SNI），不二次解析 |
| 重定向 | 手动逐跳跟随（≤4 跳），**每一跳重新校验**；重定向响应体直接丢弃 |
| 超时 | 总时限覆盖连接 + 响应头 + 响应体（挡慢速滴流），不是只看 socket idle |
| 类型 | 按**魔数**判定 PNG/JPEG/GIF/WebP，不看扩展名 |
| 字节 | 先按 base64 长度估算再解码（避免超大分配），解码后再复核 |
| 像素 | 解析宽高（PNG/JPEG/GIF/WebP），超限拒绝；**解析不出宽高时放行**（见契约 §3.2） |
| 本地路径 | 只在配置了 `snowlumaDir` 时启用；`realpath` 必须落在该目录内，必须是普通文件 |

失败一律返回**分类错误码**，不混成一个"失败"：

| 码 | 含义 |
| --- | --- |
| `E3101` | 没有可用的取图来源 |
| `E3102` | 网关 `get_image` 失败或无字节 |
| `E3103` | URL 抓取失败（DNS/连接/HTTP 状态） |
| `E3104` | 被安全策略拒绝（私网、凭据、非 http(s)、重定向到私网） |
| `E3105` | 类型不是 PNG/JPEG/GIF/WebP |
| `E3106` | 超过字节上限 |
| `E3107` | 超过像素上限 |
| `E3108` | 本地缓存路径越界 / 非普通文件 / 未配置目录 |
| `E3109` | 超时 |

## 6. 降级矩阵

| 开关 | 能力探测 | 行为 | 界面显示 |
| --- | --- | --- | --- |
| 关 | 任意 | 不取图、不提交，占位符附说明 | 未启用 |
| 开 | `true` | 正常带图 | 正常读图 |
| 开 | `false` | 不取图，占位符附"模型不支持" | 已开启但模型不支持 |
| 开 | `null`（未探测） | **仍然带图**；上游拒收则去图重试一次 | 已开启（未探测） |
| 开 | 任意 | 本回合全部取图失败 | 已开启但本回合被挡下 |

三条必须记住的口径：

1. **`null` 不等于 `false`**。"没测过"和"测过且不支持"要分开显示，否则用户
   看到"不支持"就再也不会试了——而真相只是一次探测超时。
2. **取图失败不写进能力结论**。网关抖动 → 图片取不到 → 若记成"模型不支持"，
   这个错误结论会一直留在配置里，并且每次启动都显示。
3. **上游拒收图片只去图重试一次，也不写进能力结论**。一次 400 可能是图片太大、
   可能是中转临时故障；把它固化成"不支持"会污染那个语义。

## 7. 历史持久化与重启

`state/sessions.json` 里每条消息可以带：

```json
{
  "media": [
    { "kind": "image", "file": "ABC123.image", "mime": "image/png",
      "bytes": 20480, "width": 800, "height": 600, "name": "ABC123.image" }
  ]
}
```

**只有这七个键**（`kind` + 六个元数据键）。`url` 与 base64 永远不落盘：

- URL 带 QQ 的临时鉴权参数（`?term=2&rkey=...`），写进明文会话文件等于
  把一张私有图片的长期入口留在磁盘上；
- base64 会让 `sessions.json` 涨到几 MB，而它每次启动都要全量解析。

重启之后 URL 必然丢失，这是**预期行为**：取图退回 `get_image`（缓存名通常还在）。
缓存名也丢了的那条消息会降级成"有图但取不到"，界面如实显示——不会假装没有图。

**老数据兼容**：没有 `media` 字段的历史文件照常读取，`media` 是可选字段，
不存在时行为与改造前完全一致。

## 8. 工具：`qq_message_images`

模型可以主动读某条消息里的图：

```js
// 返回的形状（由 agent-loop 转成真正的图像内容，不是 JSON 里的 base64）
{ text: '消息 123 的图片：1 张可读', images: [{ dataUrl, mime, label }] }
```

`agent-loop` 的回灌方式（为什么必须这样）：

1. `tool` 角色的消息**只放文本**，并注明"（附 N 张图片，见下一条消息）"；
2. 紧接着追加一条 `user` 消息，`content` 为 `[text, image_url]`。

如果反过来把 base64 放进 tool 的 JSON 文本里，它会在
`wrapToolResult` 的 8000 字符处被截断——模型拿到的是一段**残缺的 base64**，
它看不懂、也不会报错：工具"成功"了，图却从没进过上下文。

开关关闭时工具仍出现在清单里，但调用会立刻返回一句明确说明（不取图）。
理由见 `src/tools/chat-image.mjs` 的文件头：运行期增删工具会让工具面变成可变量，
静态审计就失效了。

## 9. 用量记账

多模态之后 `content` 可能是数组。直接 `content.join()` 会产出 `[object Object]`，
导致缺 `usage` 时的 token 估算几乎归零——表现为"账单和界面数字对不上"且**不报错**。

所以记账走 `messagesToPlainText()`：只取 `type === 'text'` 的项，图片记为
`[图片]` 占位符，绝不把 base64 拼进去。

## 11. 已知边界（本轮不做）

- **不做独立视觉模型转述**：默认复用当前聊天模型的视觉能力。用户想用更便宜的
  视觉模型转述，属于另一套架构（要引入第二个端点与会话状态），本轮明确不做。
- **视频/语音/文件不进视觉链路**：只处理 `image` 段。
- **缓存不落盘**：进程重启后要重新取图。落盘意味着在磁盘上长期留一份聊天图片副本，
  与"会话文件只存元数据"的边界冲突。
- **`face`（QQ 表情）不解析**：它需要另一套表情资源接口，本轮不涉及。
