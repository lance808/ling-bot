# 回复分条协议

> 状态：**已实现**（2026-10-23 第 1 版）。实现在 [src/reply/](../src/reply/)。
> 这份文档是**协议契约**：模型写什么、解析器认什么、坏输入怎么降级、发送层守哪些不变量。

---

## 1. 问题

此前一个回合结束后把 `result.text` **整段**交给一次 `sendText`。模型即使把回复写成两段、中间还空了一行，在 QQ 里也只是一个气泡 —— 读起来像一口气说完，而真人聊天是分几条发的。

但**不能**按逗号、句号或所有换行机械拆分：

| 拆法 | 后果 |
| --- | --- |
| 按句号拆 | 一句话被切成几个没有主语的碎片 |
| 按逗号拆 | 比句号更碎，等于把语气词都拆出去 |
| 按换行拆 | 代码块、表格、列表全碎；模型爱空行，条数不可控 |

所以边界必须**由模型显式给出**，而且必须**可校验**。

---

## 2. 协议

模型要分条时，把整个回复写成一个围栏块，语言标记是 `ling-msgs`：

````text
```ling-msgs
["第一条完整的话", "第二条完整的话"]
```
````

- 围栏内容必须是 **JSON 字符串数组**。
- 每个数组元素 = 一个 QQ 气泡，数组顺序 = 发送顺序。
- 没写这个块 = 整条发出（**默认行为，也是大多数情况的正确行为**）。

### 为什么用围栏，而不是裸 JSON 数组

裸 JSON 会和正常回答撞车：用户让模型"写一个数组示例"时，那段示例就是合法 JSON 数组。`ling-msgs` 这个标记只属于本协议，模型写代码示例时不会用它。

### 为什么不用"空行分段"

空行不可校验：模型在代码块里空一行就会被切开；而"整段只有一句"时又不能因为没空行就判断它不想分条。结构化列表没有这个歧义。

---

## 3. 校验规则

解析器（[split.mjs](../src/reply/split.mjs) 的 `parseSplitBlock`）要求**全部满足**，否则整段降级成一条普通消息：

1. 文本里恰好有一个 `ling-msgs` 围栏（多个时按顺序逐个处理，见 §4）；
2. 围栏内容是合法 JSON；
3. 顶层是数组；
4. 每个元素都是字符串（**不做 `String()` 转换**）；
5. 至少有一个非空元素。

| 失败情形 | `reason` | 实际行为 |
| --- | --- | --- |
| 没有围栏 | `no-block` | 整条原样发 |
| JSON 不合法 | `invalid-json` | 整条原样发（含那个坏围栏） |
| 顶层不是数组 | `not-array` | 整条原样发 |
| 有非字符串元素 | `non-string-item` | 整条原样发 |
| 数组为空 / 全空白 | `empty` | 整条原样发 |

**为什么不做 `String()` 转换**：`String({})` 得到 `"[object Object]"`。把它发出去，用户看到的是一条乱码消息；整段降级至少内容还在、还能看出模型想说什么。

**为什么不修坏 JSON**：改写模型输出比原样发出去危险得多 —— 修错了就是在替模型表态。

---

## 4. 边界情况的处理

| 情形 | 处理 | 理由 |
| --- | --- | --- |
| 围栏前后还有说明文字 | 并进相邻那一条（前→第一条、后→最后一条） | `"分两条说："` 独立成条会是个没有内容的碎气泡 |
| 又写了一个分条块（模型偶尔重复） | 拆出来的条目追加进去 | 整块原样发会让用户看到一段 JSON |
| 分条块里一段代码跨了两个元素 | 按围栏状态合回一条 | 两半都渲染不出代码，用户看到两个残块 |
| 未闭合围栏 | **原样发出**，不补 ` ``` ` | 不编造结尾 |
| 超过条数上限 | 多出来的按顺序**并进最后一条** | 丢内容是最坏的降级：用户不知道少了什么 |
| 大小写 / 多余空格 / CRLF | 都认 | 模型不一定精确复刻标记 |

---

## 5. 发送链路

实现在 [send.mjs](../src/reply/send.mjs) 与 [deliver.mjs](../src/reply/deliver.mjs)。

```
模型文本 ──split──▶ 消息数组 ──sendBurst──▶ 逐条 send() ──▶ 记账
                        │                        │
                    clampToMax              每条的发送闸门
```

### 不变量

1. **每条都过同一道闸门**。`send` 由调用方注入（`index.mjs` 里就是唯一的 `sendText`），白名单、出站审计、限流对**每一条**单独生效 —— 不是"整段检查一次、然后拆开发"。
2. **同一会话严格串行**。per-convKey 的 Promise 链（`createSequencer`）。两个回合几乎同时结束时，后来的排队等前一个发完，不会出现 `A1 B1 A2 B2`。串行器**在进程内共享一份**，这是"按顺序"成立的前提。
3. **条间有间隔**，范围 100–10000ms（默认 800）。
4. **中止停在消息边界**。检查在**每条发送之前**，不是只查一次；间隔中的等待会被 abort 立刻结束。已发出的不撤回，如实返回"发了几条"。
5. **部分失败继续发**。一条失败不让后面的全不发（限流通常是瞬时的），失败项带 `index/text/code/message` 回传给调用方。
6. **历史只记真正发出去的**。被限流挡下的那条不进上下文 —— 否则下一轮模型会以为自己说过。
7. **一次回复只记一个主动回合**，不是三条（否则 30 分钟间隔护栏会被一次回复打穿）。

### 触顶说明的位置

`truncationNotice`（工具调用已达上限 / 处理超时）拼在**最后一条**后面，不独立成气泡。它本来就应该跟着最后一条走；先拆分再拼会让它凭空变成一条新消息。

### 与发送限流的关系（**会影响可用的回复条数**）

限流是**按条**计的：`limits.maxSendPerMinute` 默认 8，一次 3 条的回复就占掉 3 次配额。这不是 bug，而是有意的 —— 从"别把群刷爆"的角度看，三个气泡就是三条消息。

但要知道它的实际后果：

| 场景 | 结果 |
| --- | --- |
| 一分钟内正常回两三个回合（每回合 ≤3 条） | 撞上 8 条/分钟，后面的回合会被 E2030 挡住部分消息 |
| 想频繁聊天 | 调大 `limits.maxSendPerMinute`，或把 `reply.maxMessages` 降到 1–2 |
| 管理员私聊 | 不受限流影响（`passSendGate` 对管理员私聊豁免） |

部分失败的处理是「继续发剩下的」：被限流挡下的那条进不了历史，其余照常发出并记账 —— 用户看到的是"少了一句"，而不是整段消失。

## 6. 配置

| 字段 | 默认 | 允许 | 说明 |
| --- | --- | --- | --- |
| `reply.splitEnabled` | `true` | 布尔 | 硬开关。关掉后即使写了协议块也整条发。 |
| `reply.maxMessages` | `3` | 1–10 整数 | 1 = 始终整条发。超过上限并进最后一条。 |
| `reply.intervalMs` | `800` | 100–10000 整数 | 相邻两条间隔。 |

- 界面：**配置 → 语言 → 分条**（[ui/src/views/reply-split.mjs](../ui/src/views/reply-split.mjs) 是分条区块，由 [language.mjs](../ui/src/views/language.mjs) 组合进《语言》页），写走 setting 通道的 `reply.*`。
- 启动校验：写错**直接 E40XX 起不来**，而不是静默夹到合法值 —— 静默夹会让人以为设置生效了，而实际用的是别的数。
- 运行时 `normalize*` 仍然存在，作为第二道兜底（别的调用方直接用 `sendBurst` 时）。

### 提示词与解析器必须同一个标记

`SPLIT_FENCE_LANG` 在 [prompt.mjs](../src/llm/prompt.mjs) 和 [split.mjs](../src/reply/split.mjs) 各导出一次，值必须相同（`test/reply-wiring.test.mjs` 断言）。两边各写一个字符串是最容易漂移的地方，而漂移的表现是"模型照着提示写了，但一条都没拆开"，且不会报错。

`maxMessages <= 1` 时提示词里**完全不提**分条协议 —— 提了但要求"只能一条"只会让模型在回答里解释这件事。
