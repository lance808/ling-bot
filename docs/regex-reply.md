# 正则回复（regex-reply）

> 状态：**内置插件**，随包提供，位于 `plugins/regex-reply/`。插件页里显示的名字是「正则回复」。
> 它是**消息接管类**插件（`in-process` + `handleMessage`），不提供任何工具。

`regex-reply` 做的事只有一件：**消息进来先过一遍你写的正则，命中就直接回，这条消息到此结束；没命中就当作没发生过，继续走 AI。**

---

## 1. 它解决什么

一句话：**能用固定答案回答的话，不要花一次模型调用。**

模型调用有成本：钱、时间、以及不确定性。但聊天里有一大批消息的答案是**写死的**——
"帮助"就是那张菜单，"打卡"就是记一次，"1"就是同意。这类消息让模型去想一遍，
得到的结果和你写死的那句一模一样，只是慢了 1~3 秒、贵了一次调用，
而且偶尔还会"发挥"成别的措辞。

所以把它拆成两条路：

| 消息 | 走哪条路 | 代价 |
| --- | --- | --- |
| 命中某条正则 | 直接发规则里写好的回复 | 一次字符串匹配，不调模型 |
| 没命中 | 原来的 AI 流程，一点没变 | 和装插件之前完全一样 |

### 什么规则适合它

| 场景 | 例子 | 为什么适合 |
| --- | --- | --- |
| 固定问答 | `帮助` → 菜单、`群规` → 那份群规 | 答案是一个常量，模型想不出更好的版本 |
| 签到 / 打卡 | `^打卡$`、`^签到\s*(\d+)$` | 输入形状固定，且**不希望**模型自由发挥 |
| 口令 / 触发词 | `^开始答题$`、`^抽签$` | 命中即执行，越快越好 |
| 帮助菜单 | `^帮助$`、`^菜单$`、`^help$` | 同上，而且高频 |
| 格式纠正 | 用户发 `1.` 这类不完整指令 → 提示正确写法 | 属于"礼貌地挡回去"，不需要理解上下文 |

### 什么不适合它

| 场景 | 为什么不适合 | 该交给谁 |
| --- | --- | --- |
| 需要上文才能回答 | 正则只看当前这一条消息，看不到"他刚才在问什么" | AI |
| 需要判断意图 | 同一句话在不同语境下意思不同（"行吧"可以是同意也可以是敷衍） | AI |
| 需要调用工具 / 查数据 | 正则只能回固定文本，拿不到实时结果 | AI（工具回合） |
| 长尾的、一次性的问题 | 每条都要写规则，维护成本远高于省下的调用 | AI |

判断标准很简单：**如果你能把答案一字不差地先写下来，它就适合；如果你希望它"看着办"，就不适合。**

## 2. 安装与启用

它是**内置插件**，不需要下载安装包：

1. 打开插件页 → 点「**重新扫描**」。列表里应出现「正则回复」。
2. 点开它，在「规则（JSON 数组）」里填规则（见 §3、§4）。所有配置项都有默认值，
   所以**不填也能保存、也能启用**——只是没有任何规则可命中，等于白装。
3. 保存 → 点「**启用**」。状态变成「运行中」，消息就会开始过规则了。

保存时如果要发的规则不合法（JSON 语法错、某条规则缺字段、正则编译失败…），
宿主会**直接拒绝这次保存并说明是第几条**，你改之前那份配置仍在。这是有意的：
宁可保存失败，也不要存进一份"看起来成功、其实一条都跑不起来"的配置。

这个插件没有工具、没有专用页面，插件页的「工具清单」里是空的——这是正常的，
它是**纯通道插件**（清单里 `handleMessage: true`、`tools: []`）。

### 改配置与改代码是两条路

它是 `in-process` 插件，与后端**同进程**运行。这一点决定了"改什么怎么生效"：

| 改了什么 | 怎么生效 | 界面提示 |
| --- | --- | --- |
| 改**配置**（规则、限频、冷却…） | **立即生效**：保存时宿主 dispose → init，入口用新的 `?v=` 时间戳重新 import，插件读到的就是新配置 | 「配置已保存并已生效」，`restartRequired: false` |
| 改 `plugins/regex-reply/lib/` 或 `index.mjs` 的**代码** | **必须重启后端**才彻底生效 | 插件包被替换后列表里出现「有更新待重载」，点「更新」或重启后端 |

**保存配置不会提示重启**，因为它真的不需要——保存只写了 `config.json`，一个代码文件都没动，
而紧接着的重新初始化已经把新配置读进去了。对"改一条正则"这种日常操作来说，这句提示
如果有，只会让人以为规则没生效，然后反复保存。

**改代码走另一条路。** 第二条不是这个插件偷懒，是宿主的既有语义：ESM 的模块缓存以 URL 为单位。
宿主重新初始化时会用带时间戳的 URL 重新 `import` 入口，所以 `index.mjs` 本身是新的；
但它内部 `import` 的 `./lib/*` 仍是**同一个 URL**，拿到的还是上一次的模块实例。
只有重启进程才能把整棵模块树清掉。

所以代码更新不靠"保存配置"这条路径告知，而靠**插件包被替换**这个信号：插件页会发现
`hasUpdate` 并给出「更新」按钮（`plugin.reload`）。配置保存与代码更新本来就是两个动作，
不该共用一句提示——混在一起的后果是两者都说不清。

所以简记：**改规则 → 保存就行（已生效）；改代码 → 重启后端（或用「更新」重载）。**

## 3. 配置项

| 项 | 类型 | 默认值 | 取值范围 | 说明 |
| --- | --- | --- | --- | --- |
| `rules` | textarea | `"[]"` | 最长 60000 字符 | 规则数组的 JSON 文本，见 §4。空数组（默认值）合法：插件正常运行，只是没有任何规则可命中 |
| `enabled` | boolean | `true` | — | 插件级总开关。关掉后所有规则都不跑（插件仍处于启用状态，只是不接管消息） |
| `defaultCooldownMs` | number | `0` | 0 – 86400000（整数） | 规则没写 `cooldownMs`（或写了 `0`）时用的默认冷却，单位毫秒。`0` = 不冷却 |
| `maxRepliesPerMinute` | number | `6` | 1 – 60（整数） | 全局每分钟最多回几条。**所有规则、所有会话合起来算** |
| `maxRepliesPerHour` | number | `60` | 1 – 600（整数） | 全局每小时上限，同上 |
| `maxInputLength` | number | `500` | 1 – 4000（整数） | 超过这个长度的消息**直接不匹配**（不是截断）。超长消息本来就几乎不会是"口令" |
| `matchTimeoutMs` | number | `50` | 5 – 500（整数） | 一条消息上所有正则匹配的总预算，超时降级为"未命中"，见 §9 |
| `multiMatch` | enum | `"priority"` | `"priority"` / `"all"` | 多条规则同时命中时怎么办，见 §6 |
| `replyOnSendFail` | boolean | `false` | — | 回复发送失败时是否在原会话补一句提示，见 §8。**无论开关如何，都不重试、不回退 AI** |

几个默认值为什么是这些数：

- **`maxRepliesPerMinute: 6`**：真人聊天一分钟能连发十条是因为每条都是"想说"，而正则回复是"机械触发"。
  6 条/分钟已经能覆盖帮助、签到、口令这类正常使用；再高就该怀疑是有东西在循环触发了。
- **`maxInputLength: 500`**：规则是给"短口令"用的。一条 2000 字的消息几乎不可能靠正则精确命中，
  而让长文本进规则匹配只会浪费匹配预算。
- **`matchTimeoutMs: 50`**：正常的正则匹配是微秒级的，50 毫秒是一个极宽的余量。
  它真正防的是**灾难性回溯**（见 §9），那种情况下拖多久都不够，所以要有一个硬上限。

## 4. 规则字段

`rules` 是一个 JSON **数组**，每个元素是一条规则：

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| `id` | **是** | `^[a-z][a-z0-9_-]{1,40}$`（小写字母开头，2–41 字符）。同一份配置里唯一。**它是稳定标识**：改名视为另一条规则（冷却、日志里的 `ruleId` 全都跟着变） |
| `name` | 否 | 显示名，≤60 字符。缺省用 `id`。只用于日志与说明，不参与匹配 |
| `enabled` | 否 | `true`（默认）/ `false`。关掉一条规则不用删掉它 |
| `pattern` | **是** | 正则**本体**，≤500 字符。**不要写 `/.../` 包裹**，直接写 `^帮助$` |
| `flags` | 否 | 只允许 `i` `m` `s` `u` 的组合。`g` / `y` 会被**拒绝并报错**；`u` 由插件自动补上 |
| `reply` | **是** | 回复模板，1–1000 字符，支持变量，见 §5 |
| `priority` | 否 | 整数，`-1000` – `1000`，默认 `0`。**越大越先**，见 §6 |
| `scope` | 否 | 生效范围，见下 |
| `cooldownMs` | 否 | 整数，`0` – `86400000`。不写**或写 `0`** 都表示"用配置里的 `defaultCooldownMs`"（见下方说明） |

> **关于 `cooldownMs: 0`**：它并不等于"这条规则永不冷却"，而是"没有单独设定"
> ——实际生效的是配置项 `defaultCooldownMs`。想让某条规则不冷却、但全局默认又要
> 保留时，把 `defaultCooldownMs` 保持 `0`，在需要冷却的规则上单独写 `cooldownMs`。
> 这个偏差是已知的：区分"显式 0"和"未填"需要在规则里多存一个字段，
> 而两者的意图在绝大多数配置里是同一个。

几条配套规则：

- 一份配置最多 **64 条**规则。超过会整批拒绝，不是只加载前 64 条——"我明明写了 70 条"
  和"只有 64 条生效"之间的差异，用户很难自己发现。
- 规则数组里**任何一条**不合法（少 `id`、`pattern` 编译失败、`reply` 为空…），
  整份配置都会保存失败，并指出是第几条。不做"跳过坏的、保留好的"：
  那会让用户以为某条规则生效了，实际上它从来没跑过。
- **未知字段**（比如把 `priority` 写成 `priorty`）不会导致失败，但也不会生效。
  它被当作"没写"，于是你的规则以默认优先级运行，而配置里看起来明明写了。
  拼写检查值得花三十秒。
- `pattern` 与 `reply` **不做 trim**：前后空格可能是刻意的匹配目标或文案排版。
  只拦真正的空串（`reply` 全空白也算空）。

### `scope`：这条规则在哪些会话生效

```json
{ "kinds": ["group"], "ids": ["123456789"], "excludeIds": ["987654321"], "adminOnly": false }
```

| 字段 | 说明 |
| --- | --- |
| `kinds` | 数组，取值 `"group"` / `"private"`。缺省或写 `null` = 两种都生效；**但空数组 `[]` 会报错**——"这个 scope 什么都不生效"应该写成 `enabled: false`，而不是一个语义暧昧的空范围 |
| `ids` | 白名单，最多 200 项。**填群号 / QQ 号本身**，纯数字（`^\d{1,20}$`），**不要带 `group:` / `private:` 前缀**——"群还是私聊"由 `kinds` 表达，加前缀既冗余，又会出现 `kinds: ["group"]` 配 `ids: ["private:456"]` 这种自相矛盾却校验得过的配置。空数组 = 不按 id 限制。JSON 里直接写数字（`123456789`）也接受，内部统一按字符串比较 |
| `excludeIds` | 黑名单，最多 200 项，格式同 `ids`。**优先级高于 `ids`**："在 100 个群里生效但排除其中 1 个"写成 `ids: []` + `excludeIds: ["那一个"]` 即可 |
| `adminOnly` | `true` 时**只对管理员生效**：管理员发这条消息会命中，其他人发同样的文本不命中（会按"未命中"继续走 AI）。判定是 fail-closed 的：宿主说不出"这个人是管理员"时一律按非管理员处理，于是规则不生效——宁可规则暂时不灵，也不要因为它判不出来就对所有人放开。这里的"管理员"指**核心管理员**（`config.admin.qqIds`，勾了 `inheritWhitelist` 时还包含白名单私聊），**不是** `config.silence.adminIds` |

判定顺序是：类型不在 `kinds` → 否；命中 `excludeIds` → 否；`adminOnly` 但非管理员 → 否；
有 `ids` 但没命中 → 否；否则生效。

### 最小示例（可直接粘进 `rules`）

```jsonc
[
  {
    "id": "help",                  // 稳定 ID：小写、2–41 字符、这份配置里唯一
    "name": "帮助菜单",             // 可省略，省略时日志里显示 id
    "enabled": true,               // 可省略，默认就是 true
    "pattern": "^帮助$",            // 正则本体，不要写 /.../ 
    "flags": "u",                  // 可省略；i/m/s 可选，u 会自动补
    "reply": "{user} 你好，可用指令见群公告。",  // 模板，见 §5
    "priority": 10,                // 越大越先；同优先级按书写顺序
    "scope": { "kinds": ["group"], "ids": [], "excludeIds": [], "adminOnly": false },
    "cooldownMs": 0                // 0 = 跟随配置里的 defaultCooldownMs（默认 0，即不冷却）
  }
]
```

> 上面这份带 `//` 注释，**只是为了在文档里讲清楚每个字段**。
> `rules` 的值是 JSON，**JSON 不支持注释**，实际填的时候要把 `//` 和它后面的内容全部删掉。
> 可用的完整示例见 [`plugins/regex-reply/examples/rules.sample.json`](../plugins/regex-reply/examples/rules.sample.json)（纯数据，没有注释）。

### 最容易踩的坑：反斜杠要写两遍

`pattern` 的值是**嵌在 JSON 字符串里的**，所以正则里的反斜杠要经过**两层**转义：

| 你想让正则收到的 | `rules` 里要写 |
| --- | --- |
| `\d`（数字） | `"\\d"` |
| `\s`（空白） | `"\\s"` |
| `\w`（单词字符） | `"\\w"` |
| `\.`（字面点号） | `"\\."` |
| `.`（任意字符） | `"."` |

**直接写 `\d` 是错的**：`\d` 在 JSON 里不是合法转义序列（严格解析器会直接报错），
而宽松一点的解析路径会把 `\d` 变成字面的 `d`——于是规则从"匹配数字"变成"匹配字母 d"，
症状是"这条规则从来不生效"，但配置里看起来完全正常。

同理，`\n`（换行）在 JSON 里**是**合法转义，会被解释成真的换行字符。
想让正则收到 `\n` 这个转义序列本身，要写 `"\\n"`。

一条自查方法：把 `rules` 里的字符串**打印出来**看一眼。你应该看到 `^\d+$`，
如果看到 `^d+$`，就是少写了一层反斜杠。

## 5. 捕获组与模板变量

`reply` 是一个模板，`{...}` 会被替换成对应的值：

| 写法 | 含义 |
| --- | --- |
| `{0}` | **整段匹配**（整个匹配到的文本） |
| `{1}` … `{N}` | 第 N 个**捕获组**。`N` 最大到 **20**（超出的组被忽略） |
| `{命名组}` | 命名捕获组，如 `(?<name>...)` → `{name}` |
| `{user}` | 发送者昵称 |
| `{userId}` | 发送者 QQ 号 |
| `{convKey}` | 会话键，形如 `group:123456` / `private:456789` |
| `{convId}` | 会话 id，即 `convKey` **去掉 `group:` / `private:` 前缀**后的纯数字 |
| `{group}` | 群号；**私聊里是空串** |
| `{ruleId}` | 命中规则的 `id` |
| `{rule}` | 命中规则的显示名（没写 `name` 时就是 `id`） |
| `{time}` | **本地时间** `HH:mm:ss`（不是 UTC） |
| `{{` / `}}` | 转义成字面量 `{` / `}`，不参与替换 |

**解析优先级：数字索引 → 命名捕获组 → 内置变量。** 所以给捕获组起名 `user`
会遮住内置的 `{user}`；这不是推荐做法，但至少行为是确定的。

### 未知变量与越界捕获组都替换成空串

这是刻意的：模板里写错一个变量名（`{usr}`、`{userID}`），或者引用了不存在的捕获组
（正则里只有 1 个组却写 `{3}`），结果是**那一小段变成空白**，而不是让整条回复变成
一段报错文本。文案写错不该把功能变成故障——何况报错文本发到群里更难看。

代价是"写错了看不出来"。排查时看插件页的最近日志：命中的规则 id 与最终发出的文本都在那里。

### 例子

**1. 捕获组：把输入里的数字拿出来用**

```jsonc
{ "pattern": "^签到\\s*(\\d+)$", "reply": "{user} 第 {1} 天签到成功（{time}）" }
```

输入 `签到 7` → `小鲸鱼 第 7 天签到成功（14:32:05）`。
注意这里 `\s` 和 `\d` 都写了两层反斜杠（见 §4 的坑）。

**2. 命名组：可读性更好**

```jsonc
{ "pattern": "^改名叫(?<name>.+)$", "reply": "好，以后我就自称「{name}」" }
```

输入 `改名叫旺财` → `好，以后我就自称「旺财」`。
命名组在正则变复杂时比 `{1}` `{2}` 好维护得多——改一下组的位置，模板不用跟着改。

**3. 内置变量 + 转义大括号**

```jsonc
{ "pattern": "^我是谁$", "reply": "你是 {user}（{userId}），在 {convKey}。想看原话就发 {0}。字面量写法：{{user}}" }
```

输入 `我是谁` → `你是 小鲸鱼（123456），在 group:1001。想看原话就发 我是谁。字面量写法：{user}`。
最后那段演示了 `{{` / `}}`——想让大括号**原样**出现时用它（此处 `{{user}}` 不会被替换成昵称）。
注意 `{0}` 是整段匹配，也就是输入本身。

**4. 全角字符与 `u`**

```jsonc
{ "pattern": "^[０-９]+$", "reply": "收到全角数字：{0}" }
```

`u` 会自动补上，所以 `\u{...}`、`\p{...}` 这类写法可以直接用；
但要注意开了 `u` 之后，一些老写法（如裸的 `\-`）会变成非法转义，保存时会直接报编译错误。

## 6. 多条规则同时命中怎么办

一条消息同时被三条规则匹配到，是很常见的（`查状态` 和 `查状态 详细` 会同时命中最宽的那条）。
处理顺序与去重规则如下。

### 先排序：`priority` 降序，同优先级保持书写顺序

- 排序键是 `priority`，**降序**（大的在前）。默认 `0`，范围 `-1000` – `1000`。
- `priority` 相同时，**保持 `rules` 数组里的书写顺序**（稳定排序）。

第二条很重要：如果同优先级还按别的规则排（比如按 id 字母序），那么"把规则上移一行"
就变成了一个没有任何可见效果的操作，而用户会以为它生效了。

### `multiMatch: "priority"`（默认）：只回最高优先级那一条

命中多条时，**只有排在最前的那条会有回复**，其余命中只写进日志（`ruleId` 会出现在日志里）。

为什么默认是这个：

- **一次消息回多条读起来像刷屏。** 用户发一句"查状态"，收到三条不同详略的状态，
  第一反应不是"信息真全"，而是"这机器人怎么了"。
- **规则作者很难预期叠加效果。** 两条规则分别看都对，同时命中时的组合文本却可能是
  前言不搭后语的两截。让"叠加"变成一个需要主动开启的选项，默认行为才是可预期的。

所以想让"精确规则"赢过"宽泛规则"，**给精确的那条更高的 `priority`**，
而不是指望"两条都会回、看得懂的人自己挑"。示例文件里的 `status-any`（`0`）与
`status-detail`（`100`）就是这种搭配：输入 `查状态 详细` 两条都命中，回的是精确的那条。

**一个容易误会的点：不回退。** 只回最高优先级那条，意味着如果**它**这次被跳过
（`scope` 不适用、还在冷却、渲染出空文本），插件**不会**退而求其次去回第二优先级的规则
——这次就是没人回，消息交回 AI。理由是：能兜底的那条通常就是被特意压低优先级的宽泛规则，
"精确规则暂时不可用 → 换成宽泛规则" 会让回复内容在一段时间里莫名其妙地变样，
而用户完全看不出这是冷却造成的。宁可这次交给 AI（它至少知道上下文），也不做这种静默替换。

### `multiMatch: "all"`：按优先级各回一条，但最多 3 条

开启后，每条命中的规则都会回一条，**顺序按 `priority` 降序**。
上限是**一条消息最多 3 条**——这个数字对齐宿主既有的防刷屏上限
（一次工具调用最多发 3 条消息，见 `docs/plugin-api.md` §5.3 的「发送限制」）。
超过 3 条的部分不会发，只记日志。

这个上限不是性能考虑：一旦允许无上限，一条写宽了的正则（比如 `.*`）配上十条规则，
就能让机器人瞬间把群刷爆，而它可能紧接着就被限流或踢出。

> 建议：先用默认的 `priority`。只有当"多条回答确实各自独立、并且你希望用户都看到"时
> 才开 `all`——比如一条回"已记录"、一条回"当前排名"。

## 7. 冷却与限频

三层限制，从窄到宽：

| 层 | 作用范围 | 由谁控制 | 超限后果 |
| --- | --- | --- | --- |
| 单规则冷却 | **同一条规则 + 同一个会话** | 规则的 `cooldownMs`（或 `defaultCooldownMs`） | 这**条规则**这次跳过；同一批里其它命中的规则照常判（不是整条消息交给 AI） |
| 每分钟上限 | 全部规则 + 全部会话 | `maxRepliesPerMinute` | 整条消息**不接管**，继续走 AI |
| 每小时上限 | 同上 | `maxRepliesPerHour` | 同上 |

三层是**串联**的：限频在匹配之前判（额度没了就不必花 worker 的时间），冷却在命中之后判
（它要和"哪条规则"绑定）。所以限频用满时连正则都不会跑。

几个必须说清的点：

1. **冷却只在发送成功后才计入。** 检查与占位是两步：先判断"这条规则是不是还在冷却期"，
   真的把回复发出去了，才记下这次时间。发送失败（被闸门拒绝、网络异常）
   **不消耗**冷却，也不占用限频额度。否则一次偶然的失败就会把这条规则锁住一段时间，
   而用户看到的是"这条规则突然不灵了"，过一会儿又自己好了——最难排查的那种症状。
   注意这不等于"会重试"：失败就是失败，见 §8。

   这个做法有一个诚实的代价：在"发出去了、但还没来得及记账"的那几毫秒里，
   如果另一条消息并发进来，它可能也通过同一道检查——结果是**最多多发一条**。
   这比"失败也记账"要好：前者偶尔多一句，后者会让规则在失败后莫名哑火。

2. **冷却表与限频计数都在内存里，重启清零。** 这是**有意**的。用户重启程序，
   最常见的动机就是"让它恢复正常"；如果这些状态也持久化，重启完规则还锁着，
   那个操作就没意义了。代价是重启后短期内可能多发几条——是"多发"，不会"少发"。

3. **限频耗尽时是"不接管"，不是"静默吞掉"。** 这条区别很重要：
   不接管 = 继续走 AI 流程，用户还有可能得到回复；静默吞掉 = 消息凭空消失。
   前者最坏只是"这次没省下模型调用"，后者是功能坏了。

4. **两种超限的粒度不同**，值得记一下：冷却命中只让**那一条规则**退出这次匹配，
   其余规则照常；限频用满则让**整条消息**不接管。前者是"这条话刚说过"，
   后者是"机器人这一分钟说太多了"——后者的判断对象本来就是整台机器。

   顺着这条还有一个边界：如果一条消息命中的规则**全都**还在冷却期，
   那这次没有任何一条规则会回，消息就**交回 AI**（而不是"假装回过了"）。
   这在"多命中"的场景里很自然，但值得知道：冷却可以把一条本该被插件接住的消息
   推回 AI 流程。

5. 想彻底关掉回复，用 `enabled: false`，不要试图通过把上限设成 0 来关
   ——限频的下限是 1 次/分钟，配置不允许 0。

## 8. 发送失败与重复回复

回复发送走**宿主统一的发送闸门**：白名单/黑名单、出站审计、限流都在那里
（见 `docs/plugin-api.md` §5.3）。插件自己不直连 QQ。

失败时（被闸门拒绝、或发送过程抛异常），插件的处理是：

**记日志 → 不重试 → 不回退给 AI → 这条消息到此结束。**

为什么不回退 AI：

- **回退会让同一条消息被回两次。** 发送失败时消息其实已经"被接管"了，
  再交回 AI，AI 会针对同一句话再答一遍。用户看到的是两条重复回答，
  而真正的问题（发送为什么失败）被掩盖了。
- **"闸门拒绝"本来就不该由 AI 补发。** 闸门拒绝是有理由的：会话不在白名单、
  正在限流、内容被审计拦截。换一条路径（让 AI 再发一遍）来达成"发出去"，
  等于绕开了那道闸门——而它正是为了挡住这次发送才存在的。

所以这里的取舍是：**宁可少一条，不可重复一条。** 少一条的后果是用户没收到回复，
他可以再问一次；重复一条的后果是群里出现两条一样的回答，而且没人知道为什么。

排查这条路径时看插件页的「最近日志」：失败会记录闸门返回的 `code`
（`E2020` 出站审计、`E2030` 限流、`E20XX` 白名单/黑名单），不会抛给用户。

`replyOnSendFail` 控制的是失败后的**知情**问题：开着它时，插件会在原会话补一句
"这条规则没发出去"；关着（默认）就只留日志。它**不改变**"不重试、不回退 AI"这两条。

默认关掉的理由是：**失败提示自己也要走同一道闸门**。如果这次是"会话不在白名单"
或"正在限流"被拒，那么补的那句话大概率同样发不出去；而如果它侥幸发出去了，
用户看到的是一句解释为什么没回复的回复——多数情况下这只是噪音。
需要这个信息时看日志更可靠。

## 9. 安全边界

插件在决定"要不要接管这条消息"时，会先过下面这些关。**任何一关不通过，就当作没命中，继续走 AI。**

| 关 | 规则 | 为什么 |
| --- | --- | --- |
| 不是普通消息 | 只处理 `kind: "message"` 的事件 | 拍一拍、撤回、入群请求、元事件没有"文本"这个维度，也就无所谓"命中" |
| 文本为空 | 不匹配 | 空白消息没有可匹配的内容 |
| 自己发的消息 | 永不接管 | 自己回自己会形成循环。宿主上游其实已经过滤过，插件再判一次是**故意重复**——那是唯一可能自激的一环，多一行 `if` 换掉一整类事故 |
| 插件总开关 | 配置里 `enabled: false` 时不匹配 | 那是"临时静默"：保留规则配置、不回复，消息全部交给 AI |
| 白名单 / 黑名单 | 不通过的会话不参与 | 宿主都不参与的会话，插件不该抢在前面说话 |
| 静音期 | 静音期间不回复 | 静音是用户明确要求的"别说话"，正则不该能穿透它 |
| 宿主有**待确认**的动作 | 形似确认回复的文本（`1` / `2` / `同意` / `拒绝` 等）不抢 | 这类文本归审批流，被直接答掉会让用户以为"确认过了" |
| 消息超长 | 超过 `maxInputLength` 不匹配 | 见 §3。放在匹配之前，让最坏情况连 worker 都进不去 |
| 没有发送通道 | 不匹配、记一行 warn | 匹配出来却发不出去，只会白花一次 worker 往返 |
| 全局限频用满 | 整条消息不接管 | 见 §7 |
| 规则的 `scope` 不适用 | 该规则不算命中 | 见 §4。含 `adminOnly`：管理员身份由宿主在 `gate.isAdmin` 给出，缺省按非管理员（fail-closed） |

这些关的**顺序是有讲究的**：便宜且否定性最强的排在前面（事件类型、空文本、自消息、总开关），
然后是宿主的四个硬事实（白名单、静音、待确认、管理员身份），最后才是长度、发送通道、限频与真正的匹配。
两方面的好处：最贵的操作（进 worker 跑正则）排在最后；"为什么这条消息没被接管"
在日志里只会有**一个**原因，而不是几个原因叠在一起。

### `adminOnly` 里的"管理员"是哪一份名单

这一点容易理解错，值得单独写一句。宿主的 `gate.isAdmin` 用的是**核心管理员**
（`config.admin.qqIds`；勾了 `admin.inheritWhitelist` 时还包括白名单私聊）。
在桌面端「安全」页里，它就是那个标着「管理员」的名单（不是「谁能跟我说话」的白名单）。

它**不是** `config.silence.adminIds`——那是"谁能让我闭嘴"的名单，权限范围不同。
两者混用会把"能叫它闭嘴的人"升级成"能用主人专用规则的人"。
`src/guard/admin.mjs` 明确把这两件事分开，规则里的 `adminOnly` 属于**授权**语义，
所以跟核心管理员走。

这条判定是 **fail-closed** 的：宿主说不出"这个人是管理员"时按非管理员处理，
规则对所有人都不生效。方向是刻意的——判不出来时，宁可不回，也不要对所有人放开。
所以如果你写了 `adminOnly: true` 却谁发都不回，第一件事是看「安全」页的管理员名单是不是空的
（空名单 = 没有管理员 = 这条规则对谁都不生效，这是设计而不是 bug）。

关于"审批不被抢"，还多一层结构性保证：

**派发顺序是 `normal` 先跑、`low` 后跑，而这个插件声明的是 `messagePriority: "low"`。**
`dsh-bridge` 这类审批插件是 `normal`，所以审批回复永远先经过审批插件；即使它这次没有
认领（比如确实没有待处理的卡片），才轮到本插件。这个顺序写在插件清单的
`messagePriority` 里（见 `docs/plugin-api.md` §2.7），不是靠目录名排序的巧合——
后者是"这台机器上恰好对了"，前者是"哪台机器上都对"。

### 正则跑在 worker 线程里，带总预算超时

灾难性回溯（catastrophic backtracking）是正则的经典陷阱：`^(a+)+$` 这种写法
碰上 `aaaa...b` 会指数级爆炸，一条消息就能把 CPU 吃满几秒到几分钟。
这种事**不能**发生在后端主线程上——那会让整个程序卡住，连"停止"按钮都点不动。

所以：

1. 匹配在 **worker 线程**里执行，主线程只等结果（它自己也带总预算）。
2. 一条消息的匹配有**总预算** `matchTimeoutMs`（默认 50ms），到点就放弃。
3. 超时 = **终止 worker、重建一个、这条消息降级为"未命中"**（继续走 AI）。
4. 超时的那条规则进**运行时跳过表 5 分钟**，期间不再拿它跑，避免每条消息都卡满预算。

结果就是：灾难性回溯**最多拖慢一条消息**，不会卡死后端；而被拖慢的那条消息
仍然会走 AI 流程，用户不一定察觉。带病的规则自己会被晾在一边，不会一直祸害所有人。
跳过表在内存里，重启即清空——修好规则后重启一下就能立刻恢复，不用等 5 分钟。

## 11. 排查

插件页 → 该插件 → 「最近日志」（宿主为每个插件保留最近 50 条）。命中与跳过的关键信息都在这里，
日志的 `message` 会直接写明是哪条规则、为什么。

| 你看到什么（日志文本片段） | 级别 | 说明 | 怎么办 |
| --- | --- | --- | --- |
| `已按规则 <id> 回复 <会话>` | info | 规则匹配上并发送成功 | 正常。若回的不是想要的文本，先看是不是**另一条**规则赢了（比较 `priority`，见 §6） |
| `同时命中 N 条规则，按 priority 只回最高一条（<id>）` | debug | 多条命中，默认只回一条 | 正常。想让精确规则赢就提高它的 `priority` |
| `同时命中 N 条规则，按上限只回前 3 条` | info | `multiMatch: "all"` 被 3 条上限截断 | 正常保护。被忽略的规则 id 都列在日志里 |
| `回复发送失败：<code> <message>` | error | 发送被闸门拒绝或异常 | 看 `code`：`E2020` 出站审计、`E2030` 限流、`E20XX` 白名单/黑名单。这不是插件的 bug，也不会重试 |
| `规则 <id> 冷却中（还剩 Nms），跳过` | debug | 这条规则还在冷却期 | 等冷却过去，或把生效的 `cooldownMs` / `defaultCooldownMs` 调小 |
| `跳过：E2030 ...` | debug | 全局限频用完了，这条消息交给了 AI | 正常保护。若频繁触发，说明规则写得太宽（比如什么消息都能命中） |
| `匹配超时，已降级为未命中（规则 <id> 已跳过 5 分钟）` | warn | 某条正则灾难性回溯 | 找出那条规则改写它。它已被临时跳过，所以症状是"时好时坏" |
| `规则 <id> 不适用于本会话（scope），跳过` | debug | `scope` 把它挡在了这个会话外 | 检查 `kinds` / `ids` / `excludeIds` / `adminOnly` |
| `跳过：宿主有待确认，且这条文本形似确认回复` | debug | 这条消息让给审批流了 | 正常，见 §9 |
| `跳过：宿主处于静音状态` / `跳过：会话未通过宿主白黑名单` / `跳过：这是机器人自己发的消息` | debug | 三种硬前置闸门之一 | 正常 |
| 保存配置时报错，提示某条规则不合法 | — | `validateConfig` 在**落盘前**拦住了 | 看提示里的条目与原因（id 非法 / flags 含 `g` / pattern 编译失败 / reply 为空…）。**这次保存没有写盘**，你改之前那份配置仍在 |
| 保存成功、但规则还是没生效 | — | 先分清改的是**配置**还是**代码** | 改配置：保存即生效（提示「配置已保存并已生效」），不需要重启；改 `lib/` 或 `index.mjs` 的代码：**要重启后端**（或等插件页出现「有更新待重载」后点「更新」）。见 §2 |
| 规则根本不命中 | — | 最常见的四个原因 | ① 反斜杠少写一层（§4）② `scope` 把它挡在了当前会话之外（含 `adminOnly` 而你不是核心管理员）③ `enabled: false` ④ 规则 id 只有 1 个字符（要求至少 2 个） |

想看更细的过程（比如"到底哪几条规则跑过"），把日志翻到 `debug` 级别看——
上面那些 `跳过：…` 与 `冷却中…` 都是 debug 级，正常情况下只在你排查时才关心。

最后一条值得再强调：**反斜杠少写一层**在配置里看起来完全正常，
唯一的症状就是"规则从来不命中"。排查顺序建议是——先打印出实际收到的 `pattern`，
再看 `scope`，最后才怀疑正则写法。

## 12. 测试覆盖

两个文件分工明确：一个只测插件自己（不启后端、不连 QQ、不调模型，`sendText` 全是假的），
一个接上宿主测"接线"是否正确。

- `test/regex-reply.test.mjs`（插件自身行为）：命中与不命中、捕获组/命名组/`{0}`/`{user}` 的模板渲染、
  越界捕获组与未知变量降级为空串、`{{` / `}}` 转义、`priority` 取最高一条、`multiMatch: "all"`
  的顺序与 3 条截断、`scope` 的 `kinds` / `ids` / `excludeIds` / `adminOnly`（含 fail-closed）、
  规则级冷却（同会话生效、不同会话不串、只有发送成功才占位）、全局限频、`defaultCooldownMs` 回落、
  `validateConfig` 与 `init` 对无效规则的双重报错（规则不是 JSON、数值越界）、
  灾难性回溯（超时 → 降级未命中 → worker 重建 → 该规则被跳过表短路）、
  静音 / 白名单 / 自消息 / 插件内 `enabled: false` 时不接管、
  审批不被抢（`confirmPending` + 确认形文本）、发送失败与发送抛异常都只尝试一次且返回 `true`、
  `replyOnSendFail` 的补提示、回复超长截断、输入超长不匹配、非消息事件与空文本、
  单条规则 `enabled: false`、全部候选因冷却跳过时交回 AI、`dispose` 之后安全返回。

- `test/regex-reply-host.test.mjs`（与宿主的接线）：真实 `plugin.json` 过清单校验、两个新字段
  （`messagePriority` / `validateConfig`）落进 manifest、旧插件取默认值、`process` 插件声明 `low` 被拒；
  `normal` 插件认领时 `low` 插件**根本不被调用**、`normal` 返回 `false` 后才轮到 `low`；
  接真实 `ConfirmRegistry` 时 `confirmPending` 为真、`low` 插件不抢确认形回复，
  静音与白名单同样在派发前被遵守；保存配置时坏规则在**落盘之前**被拦下且旧配置不被覆盖，
  合法规则能存进去并生效。

具体用例数与通过情况以 `node --test` 的实际输出为准，本文不记录数字。
